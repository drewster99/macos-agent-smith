# Acceptance validation and the acceptance contract

_Split verbatim from `CLAUDE.md` (2026-10-07); `CLAUDE.md` keeps the binding summary and links here._

### Acceptance validation (replaces Smith's routine review)

`AgentSmithKit/Evaluation/` holds the evaluator framework: `EvaluatorDefinition` (data-defined evaluation functions), `EvaluationRunner` (render slots → LLM → allowlisted tool rounds → grammar parse), and `TaskValidationCoordinator` (an `OrchestrationRuntime` extension). `EvaluatorDefaults` (in `TaskValidationCoordinator.swift`) supplies the shipped `defaultDefinition` and `makeCustomDefinition`.

Where a criterion's evaluator comes from — exactly two possibilities, resolved by `resolveValidator` purely from `AcceptanceCriterion.usesDefaultValidator` (true iff `validationPrompt` is empty). Validators are deterministic from the criterion, so nothing is stored or pinned:

1. **A non-empty `validationPrompt` → a task-scoped custom validator.** `makeCustomDefinition` wraps the prompt into a definition on the fly. This is the only route Smith can reach: `set_acceptance_criteria` requires a non-empty prompt. Smith supplies only the judgment/enumeration prompt; the SYSTEM supplies the output grammar, standard input slots, the read-only evidence-tool cap, and the limits. Never let an authored definition carry its own tool list or grammar.
2. **An empty `validationPrompt` → the shipped `EvaluatorDefaults.defaultDefinition`.** The only criterion built this way is the implicit one materialized for a criterion-less task (its descriptive name is shown to the judge, but the *stance* is the default's). `composeValidatorSystemPrompt` keys on the same predicate: default → the default's rich system prompt; custom → the criterion's prompt.

**There is no on-disk evaluator registry and no stored per-criterion validator.** Removed as unused: the `EvaluatorRegistry` struct + `evaluators/*.json` loading, the legacy seed-to-disk migration, per-task definition *pinning*, AND the `AcceptanceCriterion.Validator` enum itself (`.registry`/`.inline`) with the `validator`/`prepare` fields. Nothing ever wrote a registry file, no tool authored a stored validator, and dynamic criteria use `inputEnumeratorPrompt` (the legacy `prepare` name is gone). Old task JSON carrying `validator`/`prepare` keys still decodes — the keys are ignored, not honored. There is also no `define_validator` tool and no `custom_validator` argument. Don't reintroduce any of this without a real authoring surface to feed it.

All evaluation runs on the model assigned to `AgentRole.validator` (no per-definition model selection — the removed `ModelSlot` is documented in the git history). `CriterionVerdictRecord.validatorHash` records the `contentHash` of the exact definition that produced each verdict — the audit trail, kept even though definitions can no longer drift at runtime. A validator's `name` is `"default"` for the shipped default, or `criterion-<uuid>-validator` for a custom one.

The flow: Brown's `task_complete` puts the task in `.validating` and each acceptance criterion is judged independently (`ACCEPT` is sticky; `WAIVE` only when the criterion is waivable; `ERROR` retries once then escalates — never counted as a rejection). Rejections send a punch list DIRECTLY back to Brown. Convergence is judged by PROGRESS, not an absolute round cap: `maxConsecutiveValidationsWithoutNewApprovals` (default **8** — `OrchestrationRuntime.swift`; what it counts is in the acceptance-contract section below) — at the limit the task FAILS, never parked on Smith. Machine-can't-judge outcomes (validator errors) escalate to `.awaitingReview`, which **the USER resolves from the task row** — Re-validate / Accept / Send back / Fail (`revalidateEscalatedTask`, `acceptEscalatedTask`, `sendEscalatedTaskBackToBrown`, `failEscalatedTask`). Smith's `review_work` is RETIRED; the only surviving references are historical comments, so don't go looking for the tool. A missing validator *model* parks the task instead — see the roles section of `CLAUDE.md`. Counters reset via `resetValidationRound` on user Re-validate and Send-back, on `run_task`'s failed-task auto-reset, and on any criteria change (an edited contract gets a fresh budget). Validation is idempotent and restartable — everything lives on the task (`acceptanceCriteria`, `steps`, `validation` ledger); `.validating` tasks re-enqueue at cold boot. Don't hand routine review back to Smith, and don't make validators mutate anything — they hold the read-only evidence quartet (file_read, directory_listing, grep, glob).

**Validation telemetry: `ValidationMetricsLedger` (2026-07-28).** One JSONL row per landed verdict, appended to the GLOBAL `validation_metrics.jsonl` by the coordinator immediately after `recordCriterionVerdicts` returns `.recorded` — the single producer of verdict records, so the mirror cannot drift; superseded rounds (which wrote nothing) mirror nothing. It exists because the task-local ledger is deliberately destroyed by failed-task retry, reopen, and criteria edits, which erases exactly the contentious runs an economics analysis needs. It is telemetry ONLY — nothing in validation reads it back. Rows are flat, ISO-8601-dated, schema-versioned (`v`), and carry full traceability: task id/title, `parentTaskID` (per-template rollups), criterion id/name/waivable/default-validator flag, verdict + capped detail, round + contract version, validator name/hash, and the judging `modelID`/`providerID`. Execution truth comes from **live telemetry** (`JudgmentTelemetryBox`, a `Mutex` fed by `runValidator`'s `onResponse` across attempts and dynamic items): LLM turns, evidence tool calls, input/output/cache-read tokens, wall-clock `durationMs`, `attempts`, and `firstAttemptError` — the previously invisible rescued-retry population. Token fields are nil when only the persisted transcript was available (counts then derive from the runner's own `responseLog` rendering — acceptable for telemetry, never for behavior). Error rows also carry a typed `errorKind` (and `firstAttemptErrorKind`) via `ValidationErrorKind.classify` — a table over error messages this codebase itself composes (turn_exhaustion / timeout / transport / …; unmatched → "other", degrading a histogram, never a run; extend the table when adding an error message at the source). The file is heterogeneous JSONL discriminated by `rowKind`: per-judgment rows plus one `ValidationRoundOutcomeRow` per decided round, `outcome` typed as `ValidationRoundOutcome` (completed / user_acceptance_requested / escalated (validator error only) / failed_no_progress / rejections_returned, with settled/rejected/errored counts and the convergence counter) — including rounds that begin with every criterion already settled (Re-validate, a resubmission after send-back), which judge nothing but still decide. A passing round on a gated task is `user_acceptance_requested`, never `escalated`; outcome rows are `v: 2` (in v1 such a park was "escalated" with `erroredCriteria == 0`). Never write or compare outcome strings by hand; add a case — the task-level "how did the round end" that judgment rows cannot express. SINGLE SYNCHRONIZED WRITER, off the cooperative pool: every session's runtime shares `ValidationMetricsLedger.shared`, a final class whose one private SERIAL `DispatchQueue` does every encode+write; `append` is a synchronous fire-and-forget enqueue (deliberately NOT an actor — the validation path never suspends on file I/O, and the blocking write runs on a GCD utility thread). `flush()` exists for tests/shutdown only. Runtimes default to NO ledger — the app opts in at construction; tests that don't opt in structurally cannot write the real file (same philosophy as `PersistenceManager.init(testingRoot:)`).

### The acceptance contract (per-criterion edits; rejections keep a history)

**Decided 2026-07-26, simplified 2026-07-27, BUILT 2026-07-27** (reviewed by agy, then codex — which found the first draft unsafe — then a /stupid sweep). This describes the code as it stands. The 2026-07-27 simplification **supersedes** an earlier `archivedVerdicts` design and deletes most of it; don't resurrect that from git history. `ROADMAP.md` has the ordered build log.

- **Per-criterion verbs, and the reason is IDENTITY, not concurrency.** `CriterionAction.add` / `.update` / `.delete`, applied as a batch through `TaskStore.applyCriterionActions`. Not the argument that demoted `reorder` — Smith is single-threaded and owns criteria outright. It is that **wholesale replace mints new UUIDs**, and a new UUID is a new criterion: identity is destroyed, and with it every verdict and any hope of diffing what changed. `update` preserves `criterionID` **and `origin`**; that is the whole point of the verb. The batch is **atomic** — every action is validated against a working copy and nothing is written unless all succeed, because a half-applied acceptance contract is not a state anyone can reason about.
- **No `insert`, no `move`.** Criteria are *judged* independently, so their order is display-only. Note that `Evaluation/` now does sort by criterion position (`orderedByCriterionPosition`) — that orders REPORTING (round summary, punch list, ledger append) so a round reads the same every run; nothing sorts, indexes, or first-wins over `acceptanceCriteria` to decide *what gets judged*. **Execution independence is not semantic independence:** a validator sees one criterion, not the contract, so criterion A may say "matches the format required by the acceptance contract" and silently depend on B. Criteria must be written self-contained; that is an authoring contract, not something the system enforces. If display ordering is ever wanted it is a field on the criterion, never delete-and-re-add.
- **Rejections keep a history.** `TaskValidationState.criterionRejections`, append-only, written in `recordCriterionVerdicts` (the sole producer of verdict records, so the two cannot drift). Each `CriterionRejection` captures `criterionID`, `name`, `recordedAt`, `validationPrompt`, `inputEnumeratorPrompt`, `rejectionText` **from the criterion as judged**. It dissolves three problems at once. **Size:** a few hundred bytes per rejection instead of ~52KB per archived verdict, against an `inactive_tasks.json` already at ~21MB. **Weakening detection:** the prompts and name are captured at rejection time, so `statesSameContract(as:)` diffs them — no separate revision log. **Display contamination:** a rejection is not a `CriterionVerdictRecord`, so it structurally cannot leak into settled counts, sticky resolution, or "N of M". Nothing prunes it — not the criterion-edit retirement, not `resetFailedTask`, not `reopenCompletedTask` — so it outlives the criterion. `name` is captured because for a default-validated criterion the name IS the judging instruction. **It is currently write-only: no tool or view reads it yet**, so weakening detection is available in the data but not yet surfaced.
- **`settledCriterionIDs(in criteria:)` takes the contract it counts against** and intersects internally, so N ≤ M is arithmetically impossible to violate rather than prevented by convention at four call sites. The bare no-argument version it replaced is how "4 of 3 settled" reached the UI (2026-07-09).
- **`ValidationRoundToken` (round + contractVersion) is the staleness signal, checked INSIDE the store.** `beginValidationRound` returns it, and every mutation that COMMITS AN OUTCOME carries it: the ledger write (`recordCriterionVerdicts`), the convergence counter (`updateValidationStall`), and — via `updateStatus(…, ifValidationRoundIs:)` — the four terminal transitions (`completeValidatedTask`, `escalateValidation`, `failValidation`, `returnRejectionsToWorker`). Follow-on side effects (`addUpdate`, `clearResult`, worker teardown, channel posts) don't carry it themselves; they are sequenced BEHIND those gated transitions, so a refused transition means they never run. The exception is `escalateValidation`'s teardown, which precedes its CAS and is covered only by a snapshot check — acceptable because a criteria edit cannot land while the task is `.validating`, leaving just the zombie-run case. Both halves are load-bearing: `round` catches a second RUN on one ledger, `contractVersion` (bumped on every real criteria change) catches an EDIT, which `round` cannot because `resetValidationRound` zeroes it while keeping the ledger. Completion is in that list because status alone never gated it — a criteria edit leaves the task `.validating`, so an "all settled" decision could complete a task carrying a criterion no validator had seen. The coordinator's own snapshot check survives only as a cheap early bail and is documented as exactly that.
- **A stale round ABORTS.** `recordCriterionVerdicts` returns `VerdictRecordingOutcome.recorded(…)` or `.superseded` — never a bare `[]` meaning both "nothing qualified, carry on" and "you are superseded, stop". It is deliberately not `@discardableResult`. (The conflation was a live bug introduced by the round guard in `96a4075`.)
- **Wholesale replace is gated in `TaskStore`, on status AND evidence** — atomically, because a tool-level check is TOCTOU. `AgentTask.canReplaceAcceptanceContract(with:)` asks the narrow question: does the replacement still contain every criterion currently on the task? Restating them all destroys no identity whatever else it edits (that is the task-detail editor, which carries every row's id). Dropping one, once evidence exists, must be said through `delete`. **`hasValidationEvidence` is `validation != nil`** — the ledger's existence, not its contents, because every finer-grained signal is erased by the action being guarded: a round increments *before* judging, and a contract edit resets `round` to 0, so two edits in a row would find the second unguarded. Not parity with `purge`, which requires the strictly stronger `startedAt == nil && validation == nil`. The **task-detail editor saves as a DIFF** (`applyCriterionActions`), so a user deliberately deleting a row says `delete` instead of tripping a guard aimed at accidental loss; it has no reorder and appends new rows, so order is preserved exactly.
- **`SetAcceptanceCriteriaTool` carries `Status.isValidationContractEditable`**, the gate `ManageStepsTool` always had — enforced again in the store. There are **no mid-round criteria edits**: changing the rules while a validator judges against them is the race the gate exists to prevent. Smith can still fix criteria at both decision points, since `.failed` and `.awaitingReview` are both editable. The tool takes **exactly one of `criteria` (replace-all, first-time authoring) or `actions`**, and `get_task_details` prints criterion ids because the edit verbs have nothing to name otherwise.
- **A completed acceptance contract is immutable; changed-contract follow-ups become successor tasks (decided 2026-09-22).** `run_task` remains the correct operation for a retry or continuation when the existing criteria still describe success completely. A follow-up that adds or changes a deliverable, criterion, or distinct work phase is a new contract: Smith creates a related successor task and carries the predecessor id/title plus relevant result context into its description. Smith must not reopen a completed task merely to make its criteria editable, and must never call `set_acceptance_criteria` on that completed predecessor. This keeps the accepted result and validation ledger historically honest while still making the relationship explicit.
- **Optional per-task user-acceptance gate (decided + built 2026-10-01; hardened 2026-10-02).** `AgentTask.requiresUserAcceptance` (opt-in, default false) means a task NEVER completes on its own: once every criterion settles — or immediately, unjudged, when acceptance validation is switched off — it parks in `.awaitingReview` for the user's sign-off. The rules that make that hold:
  - **`concludeSubmission` is the only automatic exit** from validation (both all-settled paths and the validators-off path go through it), and **`TaskStore.changeStatus` refuses `.completed` for a gated task by any cause but the user's acceptance** (`TaskTransitionCause.isUsersAcceptanceOfResult`) — so `update_task`, a future caller, or a missed path fails closed. `update_task` also cannot move ANY review park (`.smithSetStatus` never leaves `.awaitingReview`), and `.validationPassed` completes only from `.validating`. **`update_task` never completes a `.validating` task (user decision 2026-10-04): `UpdateTaskStatusPolicy.permits` refuses it, and while any task is validating `completed` is dropped from the tool's status choices** via the per-turn `AgentTool.definition(for:in:)` hook (a protocol requirement, so the override dispatches through `any AgentTool`; `ToolAvailabilityContext.hasTasksInValidation`).
  - **The park's reason has one writer.** `AgentTask.awaitingReviewReason` (`.validatorError` | `.userAcceptanceRequested` | `.userAcceptanceRequestedValidationSkipped`) is derived from the entering cause (`TaskTransitionCause.awaitingReviewPark`) inside `changeStatus`, in the same write as the status, and cleared — with `validationBlockedReason` — on every exit. Never set it elsewhere. An unknown persisted value decodes as `.validatorError` (fail closed).
  - **Distinct causes**: `.userAcceptanceRequested(validationWasRun:)` parks, `.userAcceptanceGranted(validationWasRun:)` is the sign-off, `.userAccepted` is an OVERRIDE (validator-error park, or a sign-off park whose contract changed after parking). `changeStatus` refuses an accept cause that differs from `AgentTask.acceptanceResolutionCause`. Smith IS briefed on the park and the grant (SmithTaskBriefing set widened 2026-10-02).
  - **Who resolves a park is checked inside the store's CAS** (`ifResolvableBy:` / `acceptAwaitingReviewHoldingEffects`): `.user` on any review park, Smith's relay (`respond_to_user_acceptance`) only as `.smithRelayingUser(park:)` naming the CURRENT `relayableSignOffPark` (`isAwaitingOnlyUserSignOff` + its `statusRevision` + `awaitingReviewParkedAt`), so a relay authorized for one park can never resolve a later one. A config park admits nobody.
  - **A relay is authorized only by the user's own in-app message, written after the park and read by the calling Smith in its current stretch of activity** (`AgentTask.userAcceptanceRelayAuthorization`, decided 2026-10-02). `awaitingReviewParkedAt` is stamped by `changeStatus` in the park's write and cleared on exit. `InAppUserMessageLedger` (per `AgentActor`) records ONLY deliveries through `acceptChannelMessage` — the user-message buffer the app's input field uses — so an inspector direct message, another agent, or a system note never authorizes (fail closed); a record counts once `drainPendingMessages` incorporates it, and the stretch ends at the idle branch and on `/clear`. The runtime binds `callerAgentID` when it builds the tool context and requires a live Smith. The audit update cites the authorizing message id and an excerpt. Interpretation of the message stays Smith's; no control flow reads its text. A park entered before the stamp existed is row-only. The tool is offered only while a relayable park exists (`ToolAvailabilityContext.hasTasksAwaitingUserSignOff`) and stays auto-approved by the Security Agent table because its authority is structural.
  - **Changing the criteria of a sign-off park re-validates it (user decision 2026-10-04).** When an edit leaves a criterion of a validated sign-off park unjudged (added, or its judging text changed), `editAcceptanceContract` moves the task to `.validating` with cause `.signOffContractChanged` in the SAME write and publishes it from `mutateTaskOrTemplate`'s `afterLocalCommit`; the runtime's task-event consumer starts the run. Sticky verdicts mean only what changed is judged; the task then re-parks for sign-off, so an Accept is a real sign-off again. A validation-skipped park stays parked (nothing was judged). A sign-off park with an unjudged criterion can still be met in persisted data, so the predicates stay fail-closed for it.
  - **The relay's authority is deliberately strict (user-confirmed 2026-10-04)** — it ends when Smith pauses to wait (the idle transition), so a later wake such as a worker's report can never act on the user's earlier reply; Smith is told to relay first in its turn. **One post-park reply may authorize relays on several waiting tasks; this is accepted, relying on the audit update each relay writes (user decision 2026-10-04).**
  - **Cold boot re-validates only `revalidatesAtLaunch` parks** (validator errors); sign-off parks stay parked, don't hold back the launch resume, and are listed in Smith's cold-launch instruction. The task row shows a blue "Sign-off" outcome (`TaskOutcome.awaitingSignOff`).
  - **The gate is part of the acceptance contract and has one writer: `TaskStore.editAcceptanceContract`** (`AcceptanceContractEdit` = criteria change + `UserAcceptanceGateChange` with its author), so `set_acceptance_criteria`'s criteria and gate land in one write or not at all. It reaches library templates; `instantiateTemplate` copies the gate; `addTask`/`create_task` set it at creation (a new task usually auto-starts, after which the contract is locked). A gate-only change does NOT bump `contractVersion`. Turning it off is refused while `isParkedForUserAcceptance`; the worker can never change it; every real change appends an update naming its author. The user sets it in the task editor and Task Detail (`UserAcceptanceGateToggle`); `get_task_details` reports it.
- **`consecutiveValidationsWithoutNewApprovals` / `maxConsecutiveValidationsWithoutNewApprovals`** (default 8) share vocabulary; "stall" never said what stalled. It counts consecutive validation rounds in which nothing newly settled (no criterion reached ACCEPT or WAIVE — a waive counts as an approval), resets the instant anything settles, and fails the task at the limit. Persisted deliberately — the counter measures that worker and validator cannot converge on this contract, and a cold-boot reset would let a crash loop keep a runaway task alive forever; `resetValidationRound` is the intentional escape hatch. Read everywhere through the computed `validationsWithoutNewApprovals: Int`, so the persistence-shaped `Int?` never reaches the domain model.
- **Persisted keys outlive property renames.** `TaskValidationState` maps `consecutiveValidationsWithoutNewApprovals` back to the on-disk `consecutiveStallRounds` with a `CodingKeys` case (the decoder stays synthesized — a key mapping, not a hand-written `init(from:)`), so no in-flight task restarts its convergence budget at zero on upgrade. **That mapping costs the type its synthesized key list**, and the resulting footgun is real: a stored property with a default value (every optional has one) that is missing a case is silently never persisted, and every field this work added is that shape. `ledgerCodingKeyCoverage` guards it **by reflection, not round trip** — an uncovered property decodes back to its default and compares equal to any fixture that also left it defaulted, so a round-trip test stays green (verified by deliberately adding one). `SwiftLLMKit.ModelProfile` carries the identical pattern and guard.

**Known residual gap, not closed:** `ValidationRoundToken` cannot distinguish a zombie run from a Re-validate/Send-Back cycle whose contract did not change — `resetValidationRound` zeroes `round`, the successor is numbered 1 again, and the contract version matches. Closing it needs a never-resetting run epoch. `contractVersion` was deliberately NOT overloaded to cover it, because the name would then lie about what it counts. The `.validating` edit gate narrows the exposure considerably but does not remove it.
