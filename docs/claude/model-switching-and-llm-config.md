# LLM/provider configuration and live model switching

_Split verbatim from `CLAUDE.md` (2026-10-07); `CLAUDE.md` keeps the binding summary and links here._

### LLM/provider configuration

LLM provider/model state is owned by `SwiftLLMKit.LLMKitManager` (`@Observable`, on `SharedAppState`). API keys are stored in Keychain only; `ModelConfiguration` does not carry secrets. At runtime, `OrchestrationRuntime` is constructed with `(providers, configurations, providerAPITypes, agentTuning)` dictionaries keyed by `AgentRole`. The legacy `LLMConfiguration` struct is gone — do not reintroduce it.

**The shared config pool + UUID indirection was retired 2026-07-31 (user decision "retire the pool").** A role's model is now a `ModelAssignment { providerID, modelID }` stored per session (`SessionState.agentAssignments: [AgentRole: ModelAssignment]`), NOT a `ModelConfiguration.id` into a shared `LLMKitManager.configurations` pool. There is no clone-on-edit and no `ensureDedicatedConfig`. A role's runtime tuning (temperature, token ceilings, thinking, effort) is NOT a property of a shared config object — it lives entirely in the per-`(role, model)` override store (`SharedAppState.roleModelConfigOverrides`, keyed `"role/providerID/modelID"`, persisted to `role_model_config_overrides.json`) and is resolved FRESH against live `ModelInfo` at provider-build time (`ModelConfigurationOverride.resolved(against:name:)`, permissive/no-clamp, non-blocking out-of-range warnings). The model picker (`AgentModelSettingsSection`) writes `agentAssignments[role]` directly; editing an override calls `setRoleModelConfigOverride`, which fires `notifyModelAssignmentsChanged` so every RUNNING session rebuilds its providers (overrides are global; the per-session `agentAssignments.didSet → scheduleProviderRefresh` covers only the editing session's model swaps).

**A live agent follows its role's model — a retune AND a switch to a different model or provider** (retune built 2026-09-20; live model switching decided by the user and built 2026-10-05, reversing the earlier "a model change never touches a live agent"). `setProviders` compares each role's resolved configuration before merging:

- **Any change of the resolved configuration that arrives with a rebuilt provider** is pushed to every LIVE agent of that role via `AgentActor.scheduleModelChange`. The actor STAGES it in `pendingModelChange` and applies it at the top of its next run-loop iteration (`applyPendingModelChange`), the same boundary `pendingInjectedMessages` drains at. That boundary is load-bearing: it makes it impossible for one turn's LLM call, its tool results and its usage record to describe two different configurations, which is otherwise a live race because `LLMCallContext` is built AFTER every tool in the turn has run. Applied ahead of the iteration's `pruneHistoryIfNeeded`, so a changed (smaller) context window is honored by the prune preceding the next call. It also rewrites `ToolContext.currentConfiguration`/`currentProviderType`, which stamp provenance on every channel message the agent posts.
- **A RETUNE (same `providerID` + `modelID`) keeps everything else**, including `learnedMaxOutputCeiling` — a fact about the MODEL, which did not change.
- **A SWITCH (different model or provider) first makes the conversation portable** via `ModelSwitchHistory.adapt` (pure, tested in `ProviderWaitTests`). The conversation is kept; only provider-shaped data changes:
  - **ALL `continuation` is dropped on every switch**, Anthropic thinking blocks included, whatever the two providers are. Each field is an opaque signed artifact of the model that produced it. Thinking blocks are not kept even Anthropic→Anthropic: the id rewrite below edits every earlier tool turn, and Anthropic's preserved-thinking prefix check invalidates a thinking block when any earlier message (explicitly an earlier `tool_use`) changes — a 400 by default for accounts created on/after 2026-08-31 — and a third-party Anthropic-compatible endpoint never produced those signatures. Removing every thinking block is documented as always valid. Accepted cost: the earlier turns' hidden reasoning on a switch the target could have read (e.g. Opus 5 → Opus 5.5). Don't reintroduce a keep-within-family branch. Gemini then replays plain content with its documented bypass signature; Codex replays without reasoning items.
  - **Tool-call ids are reissued on every switch, per call OCCURRENCE**, to `c` + 8 digits — the one shape every supported API accepts (Mistral requires exactly 9 alphanumerics; OpenAI caps length at 40). Not keyed on provider or family: a router (`builtin.openrouter`, Hugging Face, Ollama Cloud) keeps one providerID while hosting vendors with different id rules. Not one id per distinct old id: servers that reuse `call_0` every turn would yield duplicate `tool_use` ids (Anthropic 400, permanent) and mis-named Gemini results. Results pair positionally: a result takes the first unanswered call carrying its old id in the most recent tool-call turn (FIFO — `AgentActor`'s batch-order append); an orphan or a second result for one call gets its own fresh id. Deterministic and idempotent.
  - **Edits to history no longer 400 on preserved-thinking models (SwiftLLMKit ≥ 0.0.213).** Outside a switch, this app still edits what precedes kept thinking blocks — pruning, system-prompt changes, a per-turn tool list — which on Fable 5.1 / Opus 5.5 / Sonnet 5.5 / Mythos 5.1 (accounts created on/after 2026-08-31) invalidates them with a 400 by default. The kit now sends `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` (beta `thinking-binding-controls-2026-08-01`) on every thinking request to api.anthropic.com, so an invalidated block is dropped instead; other Anthropic-format endpoints get the plain request.
  - **Switching into Anthropic with thinking on is safe.** The adapted history carries no thinking blocks, which the API accepts; a tool turn without one makes the API disable thinking for that one request instead of returning 400 ("Mid-turn conflicts degrade gracefully"; adaptive thinking doesn't require the leading block at all). Sources: platform.claude.com/docs/en/build-with-claude/thinking and /preserved-thinking, checked 2026-10-05. The earlier note here calling this "unrecoverable without editing history" is obsolete.
  - **Media** the new model can't take (images without vision, documents without document input) is removed, with a note left in the message.
  - Then it clears `learnedMaxOutputCeiling` (it described the old model) and the failure streak (fresh retry budget), and writes a non-waking note into the agent's own history, then posts a `.modelSwitched` info line naming both models — awaited, so it precedes everything the new model produces, and transcript-only (every agent drops `.modelSwitched` at ingest; as a public `.agentLifecycle` line it woke Smith and every live worker for an LLM turn each).
  - **Switching INTO a reasoning-replay model (SwiftLLMKit ≥ 0.0.214).** DeepSeek V4 (`replayReasoningContent`) requires `reasoning_content` on every earlier assistant turn of a tools request and 400s without it; turns another model wrote have none. The kit now sends the field on every assistant turn, empty when there is no reasoning — what other integrations send. Not live-verified: no DeepSeek key on the dev machine, and DeepSeek's docs don't say whether empty is accepted. If a switch into DeepSeek fails with that 400, this is the place.
- **Pushes are built from the CURRENT merged state and ordered by a generation.** Every `setProviders` merge bumps `modelChangeGeneration`; each push is built at push time (`currentModelChange(for:)`) and carries it, and `AgentActor.scheduleModelChange` drops a change older than one it already has (or was spawned with — `setModelGeneration`). Two overlapping calls each suspend once per agent, so without this an older change could land last and leave an agent on a model the runtime no longer holds. A spawn re-checks the generation right after registering (`catchUpOnModelChanges`), since a push during its build could not reach it.
- **A provider reaches `setProviders` only paired with its `ProviderAPIType`.** One without is a caller bug: the role is refused (it keeps its old provider/config/type, as on a failed build) and an `.advisory` `.error` is posted — never a guessed type, because the type is every provenance stamp. The app builds both from one `ModelProvider` lookup.
- **A role whose resolved `ModelConfiguration` is unchanged is not touched at all.** Not an optimization: the app rebuilds every role's provider on every edit, and some providers mint per-instance state (the ChatGPT-subscription provider's `prompt_cache_key`, its prefix-cache routing hint), so re-pointing an untouched role would throw away a live agent's cache locality for a change that isn't there. The MERGE still happens for every role, because provider construction also reads capability/behavior overrides that `ModelConfiguration` equality cannot see.

**Smith's context compaction and task summaries never hold anything up (2026-10-06).**
- **Task-boundary compaction runs OFF the task-event consumer** (`startAutoCompactionIfNeeded`, one at a time, a request during one coalesced into one more check). It used to be awaited there, so for its 20–30 s summarizer call every later briefing, child note and slot refill waited.
- **A summary that finishes while Smith is mid-tool-turn is HELD, not thrown away** (`AgentActor.compactConversationHistory` → `.deferredToTurnEnd`, spliced by `applyPendingCompaction` at the next loop top, reported through `onDeferredApplication`). Measured 2026-10-06: about half of all compactions were being discarded this way — a task completing wakes Smith — and the next task boundary paid for the whole summary again.
- **The splice keeps everything added after the summarized snapshot** (`AgentActor.compactionTailStart`, pure and tested). The verbatim tail is measured from the end of the SNAPSHOT, not the current history; measuring from the current end dropped, unsummarized, whatever Smith did during the summarizer call. Only the summarized middle (`[1..<tailStart]`) must still match: the system prompt and the tail are taken from the CURRENT history, so a prompt edit or a message merged into the last user turn carries over. The tail never starts on a tool result: it moves BACK onto the owning assistant turn — skipping forward could pass the snapshot's end and keep results whose call was summarized away, a request providers reject. A middle that changed (cleared, pruned, model switch) → `.historyChanged`, summary discarded.
- **Held summaries.** A summary is held (not spliced) while Smith is mid-tool-turn AND while a `/clear` or another held summary is waiting for the loop top; of two for one boundary the one covering more is kept (`.superseded` for the other); a `/clear` at the same boundary wins. No second auto-compaction starts while one is held (`hasPendingCompaction`), Stop cancels the running one (not reported as a failure), and compaction runs ONLY on the Summarizer's model — no fallback to Smith's — retried through `LLMRetryPolicy` with board-published waits (`ProviderWaitPurpose.contextCompaction`).
- **Every history rewrite marks the token estimate stale** (`markHistoryRewritten`: prune, splice, `/clear`), including one that lands during an LLM call — that call's usage then describes the longer history and is not trusted. Before this, the prune right after a splice used the pre-splice count and deleted the fresh summary.
- **Task summaries run in the background** (`summarizeAndEmbedTaskInBackground`). They are written when a task COMPLETES (validation passed, validation switched off, or the user's / Smith-relayed acceptance — all through `finishCompletion`) and when a worker ends itself mid-run with progress recorded (failed). Not on any other failure, a stop, pause, archive or delete. Awaiting the summary held up the user's Accept and Smith's `respond_to_user_acceptance` turn for its whole call.
- **A full Stop cancels background summaries** (`cancelBackgroundSummaries`; not a task start's cold path, which keeps the runtime and its store), and none starts again until the next start (`acceptsBackgroundSummaries` — a completion queued behind the Stop is reported instead). Cancelled at the top of the teardown; after the agents are down, each gets up to 2 s to unwind and each that wrote nothing is named in a user-addressed `.advisory` `.warning` ("may not have been written" if still unwinding at the limit). A cancelled call is not announced as a retry or recorded as a failure, and a summary cancelled before saving is not saved. A newer summary of the same task cancels an older one still running. Before this a summary kept billing after Stop and could land on a store the next Start had retired.

**`restartForNewTask` does NOT rebuild Smith while Smith is alive** — it cycles only the worker and returns (Phase 2, long-lived Smith). A model change reaches the live Smith through `scheduleModelChange` like any other agent.

**The non-agent holders take BOTH a retune and a model change live** (issue #9 gap 2, closed 2026-09-25). Every `SecurityEvaluator` the runtime makes (Smith's, each Brown's, the validators' shared one) is registered weakly (`liveSecurityEvaluators`). When the Security Agent's resolved configuration changes, `setProviders` hands each one the new `SecurityEvaluatorModel` (`applyModel`), keeping its accumulated review state. An evaluation snapshots its model at its start and its conversation lives only for that evaluation — except one sleeping on its provider when the switch lands, which restarts from its opening messages on the new model. The `TaskSummarizer` is switched IN PLACE (`applyModel`, via `refreshTaskSummarizerModel`; built new only when none exists) so a call it has sleeping before a retry resumes on the new model. The validator needs nothing: `validatorModel()` reads the dictionaries fresh for every criterion judgment, and a run interrupted mid-wait by a model change re-runs (`EvaluationRunner.Interruption.modelChanged`). The inspector's model line shows `AgentCardRunningModelNotice` between a change and the agent's next call. Issue #9 gap 1 (switching a live AGENT's model mid-conversation) is closed by the switch above.

**Retry sleeps are a visible, wakeable state: `ProviderWaitBoard`** (built 2026-10-05, after a Codex weekly usage limit put a whole session to sleep for 4.8 days while the UI said "Idle", "Thinking 700 min" and "Evaluating 600 min" and the Security Agent's wait was never mentioned). One board per `OrchestrationRuntime`; EVERY retry sleep — the agent run loop (provider failures only, not tool errors), Security Agent reviews and scoping, the validator runner, all three summarizer calls — goes through `ProviderWaitBoard.sleep`, publishing a typed `ProviderWait` (holder role/agent/task/purpose, `ProviderWaitReason` from `LLMRetryPolicy.waitReason` — typed, never prose — model, resume time, attempt) for exactly the length of the sleep. `setProviders` calls `wakeForModelChange(of:)` for every role whose model IDENTITY changed, LAST (after every holder has the new model), so a waiter retries on the new model at once. A change that lands while the failing call is still IN FLIGHT has no sleeper to wake, so every caller reads `modelEpoch(of:)` when its provider attempt starts and passes it to the sleep; a sleep registered after the role's epoch moved ends at once (checked under the registration lock), instead of honoring the old provider's — possibly multi-day — `Retry-After`. The app mirrors the board (`AppViewModel.providerWaits`, re-read after the main hop because hops are unordered) and `ProviderWaitStatusLabel` outranks Thinking/Evaluating/Idle in the agent cards, the inspector window header and the summarizer card; Live rows say "waiting for <model>" or "waiting on security — its model <reason>". A Security Agent review publishes the worker it holds (`ProviderWaitPurpose.heldAgentID`), and the 10-minute stall warning names that wait instead of blaming a tool. Holders without their own transcript line announce a wait once (`ProviderWait.warrantsAnnouncement`: a stated wait on attempt 1, a blip only at attempt 5). The validator's timeout excludes provider-wait time. Waits are still honored uncapped (user, 2026-10-05: don't fail a review because the provider asked to wait). `LLMRetryPolicy.sleep` was deleted — don't reintroduce a bare retry sleep.

The pool (`LLMKitManager.configurations`) still LOADS — it seeds first launch and backs one-way migration of pre-retirement state (a session's legacy `[AgentRole: UUID]` decodes into `SessionState.legacyConfigAssignments`, mapped to `(provider, model)` via the pool at load; `AppDefaults` self-migrates its bundled UUID `agentAssignments` the same way at decode and re-encodes as `agentModelAssignments`) — but no longer drives assignment. Nothing edits it: the old **Configurations** settings tab is now a per-model **Models** tab (`SettingsView.modelsTab`) listing every cached `(provider, model)` with the per-model Flags/Capabilities/Pricing editors (keyed on `providerID+modelID`, never on a config) plus Refresh Models + Export Defaults. `ModelConfigurationEditorView`, the config CRUD, `SharedAppState.updateAgentConfig`/`deleteConfiguration`, and `SessionManager.deleteConfiguration` were all deleted.

`AppDefaults` (schema v2, `defaults.json` bundled in app resources) seeds first-launch state. The `ExportDefaults` CLI target exists to regenerate `defaults.json` from the current user's installed configuration. UserDefaults-set values always win over bundled defaults.

### Loading a session never deletes its assignments

**Decided 2026-09-20 (user), after a smoke test destroyed this repo's own config.** The rule lives in `AgentAssignmentResolution.resolve` (package, tested) rather than inline in `AppViewModel.loadPersistedState`, and its contract is one line: **loading never deletes.**

- A saved assignment whose provider is not in `llmKit.providers` is **kept and reported**, never cleared. `ConfigValidationView` already renders "Provider not configured" and `start()`'s `unqualifiedRoles` guard already refuses — so a genuinely stale assignment fails VISIBLY with the user's choice intact, instead of being silently replaced by another vendor's model. This is a real behavior change: the app now refuses to start where it used to start on a substituted default.
- **Why:** the prune it replaced was guarded only by `!configuredProviderIDs.isEmpty` — all-or-nothing. A PARTIALLY loaded provider list passes that guard, so providers that had arrived kept their roles while ones still loading had theirs deleted, and `agentAssignments.didSet` persists it immediately. The old comment stated the assumption outright ("A genuinely removed single provider still prunes normally below, since the list is then non-empty"), i.e. non-empty ⇒ complete. `builtin.codex-chatgpt` is credentialed from `~/.codex/auth.json` rather than the Keychain, making it a natural straggler and the likeliest loser of that race. Same shape as the other 2026-09-20 defects: **partial state indistinguishable from deliberate removal, destructive branch silent.**
- **Healing fills; it never replaces**, so it needs no equivalent guard. It covers **every role with a bundled default**, not just `requiredRoles` — "blocks app launch" and "has a sensible default" are different questions, and conflating them is why `.validator` (deliberately outside `requiredRoles`) was the one role never healed, leaving submitted tasks parked unresolvably. `requiredRoles` still governs launch-blocking; that architecture is unchanged.
- **An EMPTY provider list reports nothing and heals nothing.** Zero providers almost always means the catalog hasn't loaded, not that the user deleted everything; flagging all of them is the same false signal in a louder voice.
- The load **logs every kept-but-unavailable assignment**. The destructive path logged only what it substituted, which is why recovering the lost values took archaeology instead of a grep.
- The validator has a row in `ConfigValidationView` that never gates Start, because an unassigned validator parks every submitted task where not even Smith can resolve it — invisible until the first task hit it.
