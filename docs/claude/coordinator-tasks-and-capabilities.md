# Worker tool grants, coordinator tasks and required capabilities

_Split verbatim from `CLAUDE.md` (2026-10-07); `CLAUDE.md` keeps the binding summary and links here._

### Worker tool grants, coordinator tasks, required capabilities (from "Tool model")

**Who decides a worker's tools (decided 2026-10-05, user).** The Security Agent scopes them; the USER may override per task (task-detail panel) and globally (Settings › Tools). **Smith cannot change a task's tools at all**: `edit_task` lost `tool_overrides` and refuses a call that still passes one (Smith had "enabled" its own `create_task`/`list_tasks`/`watch_task` on a coordinator task, the call reported success, and the worker never got them — and a Smith grant bypassed both scoping and the user's policy). **A global Never is absolute**: `ToolPolicy.effectiveApprovedTools` is the one resolution (engine and both UIs) — verdict → Always adds → per-task On/Off → Never strips LAST, so no per-task On brings it back ("it needs to work like Never sounds"); restrictions win both ways (a per-task Off also beats a global Always). No tool a user can set to Never is FORCED available: `save_memory` is approved-by-default instead (`ToolPolicy.workerToolsApprovedByDefault`, added to the base before policy), and every worker is spawned FOR its task — `ToolContext.spawnBrown` takes the task, because a task-less worker skipped scoping and every policy (`provide_help`'s crash-recovery respawn did, and now also briefs through `composeBrownTaskBriefing`). Per-task overrides only reach a worker's own candidate tools (`BrownBehavior.acceptsToolOverride(named:)`); stale overrides for other tools are listed under "Not available to workers" and reported as ignored by `get_task_details`. **A worker can coordinate other tasks (user decision 2026-10-05: "we DO have to have that ability for an agent")** — a designed capability, never an override; see "Coordinator tasks" below.

**Coordinator tasks (decided and built 2026-10-05, user; hardened by the /stupid pass the same day).** A worker can create CHILD tasks that other workers run, and wait for them.
- **Granted like any tool:** `create_child_task` and `wait_for_child_tasks` are Brown candidates in their own `BuiltInToolGroup.coordination`; the Security Agent scopes them in when the task's required capabilities call for coordination ("Create child tasks and wait for their outcomes"), within the user's policy. `create_child_task` is classified destructive AND open-world (transitively — the child's worker can hold anything) and gets a real per-call verdict judged against the CURRENT task; `wait_for_child_tasks` is pre-cleared and is a COMPANION of `create_child_task` (`ToolPolicy.companionTools`): offered whenever create is, unless the user turned wait itself Off/Never.
- **A child's text is a worker's claim, never the user's intent** (`TaskIntentProvenance`, `TaskStore.intentProvenance`). Scoping gets `taskAuthor: coordinatingWorker` plus the ORIGINATING task (first non-child up the chain); per-call review gets the same appended to the task description (`renderedDescriptionForSecurityReview(provenance:)`, keyed on `AgentTask.workerAuthoredHeading`). Requester tasks render byte-identically to before.
- **The link is `AgentTask.coordinatorTaskID`** — never `parentTaskID`, which means template lineage. `TaskStore.addChildTask` writes the whole child (criteria, steps, capabilities, retrieved context) in ONE write, because a queued child can be started by the drain at any moment. It refuses past Settings "Max child tasks per task" (default 10) counted by the persisted `AgentTask.childTasksCreated` (every child ever created — a permanently deleted or promoted one still counts), and refuses an unfinished child with the same title (`.duplicateOfUnfinishedChild`). A child cannot be promoted to a template while its coordinator is open; promotion clears `coordinatorTaskID`.
- **`AgentTask.isCoordinatingChildren` is THE "still coordinating" predicate** (active, not terminal, not a template): effect recording, delivery, departures and `get_task_details`' routing line all ask it. `childTasks(ofCoordinator:)` reads the active list AND the inactive store.
- **The coordinator stays alive and its task stays RUNNING while it waits — no new status** (user: "keeping it alive and NOT explicitly waiting"). `wait_for_child_tasks` declares `ToolEffect.waitsForChildTasks`, which parks the run loop with `WorkerPark.awaitingChildTasks`: no turns, no tools, no nudges. It parks only while some child is `ChildTaskProgress.isWaitable` (progressing, or waiting on the user/Smith/a start hold); with every child finished, or the rest stalled (paused, stopped, archived), the tool FAILS and says where each stands — a worker never parks on a child that won't move. A child's note (a broker delivery, below) wakes ONLY a worker parked for children — never one parked after `task_complete`, which leaves it queued.
- **Outcomes go to the coordinator, not Smith** (user: "coordinator only"). `CoordinatorTaskBriefing` is a second durable subscriber in `applyStatus`, recorded in the same write (`TaskEffect.coordinatorBriefing`) while the coordinator is coordinating. It reports entering completed / failed / awaiting review, AND a stall the coordinator must react to (paused/stopped by the user, Smith or a scheduled action, a lost or self-ended worker — an exhaustive cause table; capacity sheds and shutdowns are not noted). Never a start. Smith's routine notes for that child are not written; sign-off notes still go to Smith because they wait on the user. A child that LEAVES the active list unfinished, or carrying an undelivered outcome, emits `TaskStoreEvent.childLeftCoordination` (the move drops a task's effects, so the dropped outcome records travel in the event); the coordinator gets the outcome and a departure note.
- **Delivery is the notification broker (user request 2026-10-05: "we already built a notification system — use it").** Every coordinator note is a `coordinator_briefing` notification (`CoordinatorBriefingDelivery` is the one wire format) for `Recipient.taskWorker(taskID: coordinator)` — a PULL recipient with its own durable queue, lease and lease generation (leases are keyed by the full `Recipient`, so each task's worker is independent). Every task worker is wired as that recipient at spawn (`resetLease` re-hands whatever a previous worker never acknowledged). A worker drains its queue only after its briefing turn (`hasCompletedLLMTurn`, never cleared — not `llmTurns`, an inspector log a rebuild empties) and never while handed off (`.awaitingHandoff`) — `AgentActor.workerTakesQueuedNotifications`; a drained note un-parks a worker waiting on its children, and it is acknowledged when the worker next goes idle. No transcript row is posted (`childTaskOutcome` is RETIRED): the child's own status banners show the outcome. A note that REPLACED Smith's own note carries it (`smith_note`); when the coordinator stops coordinating (terminal, archived, deleted — and at cold boot for anything stranded), `rerouteCoordinatorBriefings` gives Smith the copy each never-handed note owes him (one id shared with the direct fallback, so they dedup), then takes the queue back (`NotificationBroker.reclaimQueued`, which unlike `withdraw` also takes leased items). A coordinator already gone at delivery hears nothing, and Smith gets the child's note only for a replaced cause — he already has the others. Accepted residual: the departure EVENT is not durable; a crash before it is handled loses that note, which `wait_for_child_tasks` and a respawned briefing cover by re-reading every child.
- **Admission and the drain (one overshoot per nesting level).** Base capacity rule: "Worker pool" in `CLAUDE.md`. `admitsWorker(for:)` is the ONE admission rule (start gate AND spawn backstop): below capacity, or a child of a coordinator blocked on capacity — `coordinatorsBlockedOnCapacity()`, non-empty only when EVERY live worker is parked on its children (`waitingCoordinatorTaskIDByAgentID`, worker → coordinated task). The started child is not waiting, so it is one over per level of nested coordination (the user's "allow 1 overshoot" — a strict cap+1 deadlocks at depth 2); the spawn posts an `.advisory` (`.info` one over, `.warning` beyond). `drainPendingTaskQueue` order: a WORKING coordinator's children first (`occupiesWorkerSlot`; pending, or interrupted on either resume queue — regardless of the auto-run settings), then capacity-deferred work, then the launch-resume batch, then auto-advance. Above capacity only a blocked coordinator's child starts, from any of those queues (a capacity cut or a cold launch leaves it `.interrupted`, not pending). Every committed-child start uses origin `.coordinatorTool`. The pool is read AFTER the drain's store read, drains go through the coalescing driver (`advanceAfterFreedWorkerSlot`), and a capacity change of EITHER direction drains. `automaticallyResumingChildTaskIDs()` is the one answer the drain and the wait tool share. Accepted residuals: the waiting flag is stale between a note arriving and the worker's next iteration, and a coordinator woken by a non-child message while a child runs above capacity — each at most one extra working worker, transiently.
- **A child start never takes the cold path** (`TaskStartOrigin.coordinatorTool`): that path stops every worker, the waiting coordinator included.
- **A resume refused at capacity goes back on its queue, never to `.pending`.** Two drains (or a drain and the cold-launch batch) can each see the same free slot; the serialized gate ("Worker pool" in `CLAUDE.md`) refuses the loser. An interrupted task resumed with origin `.launchResume`, `.capacityResume` or `.coordinatorTool` returns to `.interrupted` at the FRONT of its resume queue (`startAbandoned` may go `.starting → .interrupted`; no watch fires for it). Pended, it fell off every resume path and, with auto-advance off, never started.
- **A child's briefing makes no routing claim** (it is composed once; routing changes when the coordinator closes). `get_task_details` says where its outcome goes NOW (`CoordinatorTaskBriefing.routingDescription`). A respawned coordinator's briefing lists its children with their progress, as does `get_task_details`. Task Detail shows "Created by" and "Child tasks" (archived/deleted ones labelled).

**Required capabilities are their own field (decided 2026-10-05, user).** `AgentTask.requiredCapabilities: [RequiredCapability]` — what the worker must be able to DO, never tool names — replaced the "Capabilities Needed" prose `create_task` used to ask for at the bottom of the description (old tasks were not migrated; their prose still reaches the scoper inside the description). Each item carries `addedBy`, `addedAt`, an `origin` (`asWritten` | `addedLater`) and an optional `reason`; a later addition is marked as one EVERYWHERE it is shown, through ONE renderer (`RequiredCapability.renderedLine` / `AgentTask.renderedRequiredCapabilities()`).
- **Writers, all in `TaskStore`:** written whole at creation by `addTask` (`create_task`'s `required_capabilities`, the editor's Create — both through `RequiredCapability.makeAsWritten`), `addChildTask`, and `instantiateTemplate` (copies, substituted, as `asWritten`, keeping author and reason; an item that renders blank is dropped). After creation ONLY `addRequiredCapability` (Smith's `add_required_capability`, which requires a reason; the Task Detail field) and `editRequiredCapabilities` (the editor's add/reword/remove DIFF, `RequiredCapabilityEdit.edits(from:to:)`, atomic — so an item Smith adds while the sheet is open survives the save) change it, sharing one set of per-item rules (trim, template placeholder check, instance substitution, dedup, a history line naming the author for every add/reword/remove).
- **One lock rule: `AgentTask.requiredCapabilitiesLockReason`** — completed (history; follow-up is a successor task), validating (validators read the list while judging; the refusal tells Smith how the lock ends), archived/deleted. Running and awaiting help stay editable on purpose: that is when a worker's unmet need is learned. Every writer and every editing surface (Task Detail's section and add field, the editor's caption) asks it. `AgentTask.isDefinitionEditable` gates the editor and inline description edit, so Edit is not offered on an archived/deleted task.
- **Malformed list arguments are refused, not silently trimmed** (`ToolArguments.strictOptionalStringList`): `steps`, `required_capabilities` and `attachment_ids` given as a single string or with a non-string item fail the call; placeholders (`""`, `[]`, blank items) still read as absent.
- **A live worker is re-scoped even when the change lands mid-spawn:** after registering, the spawn compares the task's capabilities with the snapshot scoping used and requests a re-scope if they differ. The task editor writes the definition only when it changed (it is refused while running), and Task Detail has its own "Add capability" field for any unfinished task.
- **Every execution path applies a tool's declared effects** (`updatePostCallFlags`), the parallel batch included — it used to skip them, losing e.g. a batched `run_task`'s restart effect.
- **Readers — every agent path and every display:** the worker briefing (`## Required capabilities`, telling Brown to `request_help` with the ABILITY it lacks), `get_task_details`, `list_tasks`, the scoping payload (its own `requiredCapabilities` field), the per-call security review (`renderedDescriptionForSecurityReview`, also the validator's evidence gate), the validator's `requiredCapabilities` input slot, the Summarizer, the memory embedding text, Task Detail (its own section), the task editor, the New Task banner, and the PDF export.
- **The scoper is told to pay SPECIAL attention to the list, not to look ONLY at it** (user's words): it still reads title and description as carefully as ever, and an `addedLater` item is a need the worker actually hit.
- **A change re-scopes a live worker.** Both store writers emit `TaskStoreEvent.requiredCapabilitiesChanged` (session tasks only — no worker runs a library template); the runtime calls `AgentActor.requestToolRescope()` on the task's worker, which re-scopes at its next turn boundary against the task as it then reads. A failed re-scope keeps the previous tools and says so in the transcript (`.error`).
- **This is how a worker gets a missing ability:** Brown `request_help`s naming the ability → Smith `add_required_capability` → the Security Agent re-scopes, within the user's policy (a Never stays never). Smith never grants a tool. With tool scoping OFF there is nothing to re-scope (the worker already has every tool the policy allows); the tool's result says which case applied.
- **Scoping is shown only tools the user's policy can offer** (`ToolPolicy.scopingCandidates`, the candidates minus Never). The worker's re-scope fingerprint covers exactly that set (seeded at spawn through `enableToolScoping(approvedNames:scopedCandidateFingerprint:)`), so setting or lifting a Never re-scopes; a spawn whose every candidate is Never is refused with an error. A policy, override or scoping-setting change that lands while a worker is being wired is re-pushed right after it registers.
