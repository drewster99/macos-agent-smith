# Reliability conventions

_Split verbatim from `CLAUDE.md` (2026-10-07); `CLAUDE.md` keeps the binding summary and links here._

## Conventions specific to this repo (long-form)

- **`AgentActor.conversationHistory` has a single writer: the run loop.** External / asynchronous `.user` injections (`appendUserMessage`, and anything the runtime or `TaskValidationCoordinator` sends into an agent mid-run) must be **queued** (`pendingInjectedMessages`), never appended directly — the run loop drains them at the top of the iteration, a boundary where the previous turn is complete. This is what makes it structurally impossible to splice a message between an assistant `tool_calls` turn and its `tool_result`s (the provider adjacency rule; violating it is a non-retryable HTTP 400 that kills the agent). A concurrent writer (the validation coordinator informing Smith while he was parked in a long `save_memory`) was the original cause. The loop's own top-of-iteration writers (drains, digest, memory inject) and `pruneNonBrownHistory` (walks back past tool results, never splits a pair) are already safe. Don't reintroduce a direct external append, and don't "fix" adjacency with a silent normalizer — keep the invariant structural.
- **The Security Agent is an unconditional chokepoint: EVERY tool call from every agent routes through it.** There is no unevaluated branch left in `AgentActor` — `executeWithApproval` is the only way a tool runs, and it DENIES when no evaluator is configured rather than running the call unreviewed. The `mustEvaluate` predicate and the non-evaluated `directExecute` path were deleted rather than left as a constant-true test, so the invariant is structural instead of conditional. **`taskLifecycleTools` (`task_complete`, `request_help`, `reply_to_user`, `message_user`, `notify_brown`, `task_update`, `wait_for_child_tasks`) route too** — they used to execute with "no approval" AND no `tool_request`, making them the quietest bypass in the system; they're now pre-cleared in the auto-approve table for the roles that emit them, so a worker can still say "done" or "blocked" without an LLM sitting in the path. The table **spells those names out rather than referencing `taskLifecycleTools`** — that set answers a sequencing question, and wiring it to the security carve-out would let anyone adding a lifecycle tool silently widen what skips review (fail-open). Duplication drifts the safe way: a name missing from the table just gets a real evaluation. The validator's `securityGate` likewise fails closed (it used to be `nil` — "reads execute directly" — when no Security Agent was configured). **The Security Agent cannot recurse — not because it is toolless, but because its tools never re-enter the gate.** It holds a read-only evidence pair: `file_read` always, plus `attach_file` when the runtime wired both attachment ingest and URL resolution (`SecurityAgentBehavior.toolNames`, `SecurityEvaluator.evalTools`) — it has to be able to look at the file a call is *about* before ruling on it. Those execute INLINE inside `SecurityEvaluator` (`executeSecurityAgentFileRead` / `executeSecurityAgentAttachFile`), never through `executeWithApproval`, so an evaluation structurally cannot spawn another one. Evidence rounds are bounded by `maxToolRounds` (16), after which the model is offered NO tools and must commit to a verdict. **Whether a tool call is reviewed was REINTRODUCED as a preference (2026-08-01, `docs/claude/orchestration-settings.md`), deliberately reversing the earlier "not a preference" stance.** The Orchestration settings expose per-emitter review toggles (Agent Smith / Agent Brown / Validators); `SecurityEvaluator.evaluate` checks `reviewsToolCalls(callerRole)` FIRST and, when off, approves WITHOUT a verdict. The call STILL routes through the evaluator and is recorded + posted as "review disabled" (`SecurityDisposition.wasEvaluated == false`) — never as SAFE, and no control flow keys off the prose. The invariant preserved is VISIBILITY, not universal evaluation. The old `enablePerToolCheck` / `perCallApprovalEnabled` / `evaluatesOpenWorldToolsOnly` stay deleted — that was a different, INVISIBLE scheme (skipped calls vanished from the transcript); the new toggles keep every skipped call countable and in the transcript, which is the whole point.
- **What varies is verdict COST, not routing: `SecurityEvaluator.autoApprovedToolsByRole`.** A hardcoded `[AgentRole: Set<String>]` naming the calls approved without an LLM round-trip — still recorded, posted, and countable, so cheap never means invisible. **Fail-closed on both axes**: an unlisted role or unlisted tool gets a real evaluation, so new tools are judged until someone deliberately clears them. Smith's set covers messaging/task/scheduling/read-only inspection plus its stop controls (`terminate_agent`, `abort` — stopping is the risk-reducing direction, so a reviewer must never delay or veto one) and deliberately EXCLUDES its open-world tools and `attach_file` (its egress surface); Brown's holds only its task-lifecycle calls and read-only AppleScript discovery; the validator's is the read-only evidence set. Replacing this table with anything user-configurable reintroduces the hole it closed — the old scheme made an unreviewed tool an *invisible* one, absent from the transcript entirely.
- **The Security Agent provider is still REQUIRED regardless of the review toggles.** A missing provider fails `start()` outright (Smith's open-world tools are the softest exfiltration surface in the system, so starting Smith ungated is the one failure least likely to be noticed) and refuses `spawnBrown` — the toggles are runtime and can flip back on, so the evaluator must exist. What a review toggle changes is verdict COST, not the provider requirement: with it OFF, that emitter's calls run approved-but-unjudged (visibly, per above). A missing validator model parks tasks per the roles section of `CLAUDE.md` (unless validation itself is disabled — then the task completes flagged unvalidated), and no role falls back to another role's model (same section).
- **Every LLM call retries through `LLMRetryPolicy` — there is exactly one policy.** Transient failures (429, 408, 5xx, network) retry up to 50 attempts with exponential backoff (1s doubling, ceiling 15s); a server `Retry-After` overrides the curve and is honored **uncapped**; permanent failures (the remaining 4xx — bad key, out of credits, unknown model, malformed request) are **not retried at all**. Unknown errors deliberately classify transient — stranding an agent that would have recovered is worse than a bounded number of wasted retries. Consolidated 2026-07-25 from five divergent hand-rolled implementations (`AgentActor` 50×/3s→120s-or-1800s; `TaskSummarizer` 3×/5-15-45s; `scopeTools` 8×/500ms; the per-call security evaluator 8× with **no** backoff; the validator **once**, no backoff). The divergence was load-bearing: the evaluator burned all 8 attempts inside one ~20s Ollama Cloud outage and denied a tool call for want of a verdict, the validator gave up on the first blip and parked the task for a human, and `AgentActor` classified an out-of-credits 402 as permanent and then retried it 50 times anyway because the classification only gated the log message. Don't add a bespoke retry loop; if a caller needs different behavior, change the policy. Every retry SLEEP goes through `ProviderWaitBoard` (see `docs/claude/model-switching-and-llm-config.md`).
- **A worker model that can't be used puts the task ON HOLD, never fails it (decided 2026-10-06, user).** An account or model failure — `ProviderUnavailableKind.of(_:providerID:)`: HTTP 401 / 402 / 404, a 403 that is NOT OpenRouter's moderation refusal (typed `error.metadata` fields), or the Codex backend's depleted credits or spend cap; typed, never prose — is reported by the agent BEFORE it stops (`ToolContext.reportProviderUnavailable` → `handleProviderUnavailable`, which returns a typed `ProviderOutageHandling` the agent's stop line is worded from — it never claims a hold the runtime didn't make). Every 404 counts, OpenRouter's included: it answers 404 both for a request the model can't serve ("No endpoints found that support image input") and for a model with no provider left, and only the message tells them apart — holding tasks visibly beats failing each one started on a dead model.
  - **A 429 that outlasts the whole retry budget is one too** (user decision 2026-10-06: "leave current behavior EXCEPT that after 50 tries we pause"). A single 429 stays transient and is retried exactly as before; only when the streak ends on a 429 (`ProviderUnavailableKind.afterRetriesExhausted` → `.rateLimitExhausted`) is it reported. The resume hint is the kind's `retryCondition` ("once the provider's limit resets"). Any other exhausted streak (5xx, network) still stops the agent and fails the task.
  - **"On hold" is `.interrupted`** (`.providerUnavailable`: no watch fires; Smith is told not to restart it). User-facing text says "on hold", never "paused" — `.paused` is a different status. `workerOutage` is the breaker — the worker role only, the one tasks start on; any other role's agent just stops, with a notice each time. The user gets ONE advisory per outage.
  - **The breaker gates every start in ONE place**, `passesProviderOutageGate`, in `restartForNewTask`'s queue item ahead of the cold/live branch, so the cold path can't bypass it. A non-user start is held (told once per task); the drains start nothing; the scheduled-run queue keeps its persisted entries. `run_task` / `create_task` / `create_child_task` say it is held (`TaskCreationSupport.outageHoldNote`), and `provide_help` refuses to respawn a worker (the help request is kept).
  - **A held start is a `HeldStart` (task id + the status revision when it was held).** At the release it is started only if the revision is unchanged — so a task Smith resumed from `.paused` keeps its promised start, while one the user paused or started meanwhile has moved on and is dropped. A repeated start request for a held task updates its revision (the latest request wins). The gate re-checks the outage after its one suspension, since a model change there releases everything. Archive/delete change no status, so they drop it through the lifecycle event instead (handled asynchronously; a restore racing that handler can keep the start — accepted).
  - **Released** when the worker's model IDENTITY differs from the outage's (in `setProviders`, and re-checked at the gate), or by the user's Play (`.explicitUser`: "I fixed the account, try again"). Held starts move onto `providerRecoveredQueue`, which the drain starts ahead of capacity-deferred work regardless of the auto-run settings (a coordinator's child through the committed-children step, as `.coordinatorTool`); a start refused at capacity returns to its front. The drain runs as its OWN lifecycle step (`drainAfterOutageRelease`) — behind a Play that released it, so the Play claims its slot first — and repeats after each scheduled run it starts, since a scheduled start ends a drain pass. A model still unusable trips the breaker again.
  - **A report for a model the worker no longer has** (a call in flight across a model switch) trips nothing: the dying worker is unassigned and the task goes on `providerRecoveredQueue`, started by the drain the worker's exit runs. The model check and the breaker write have no suspension between them.
  - In memory only: a relaunch is a retry (the task update says to press Play if the app is relaunched first). A malformed request, a content-policy refusal or a context overflow belongs to one conversation and still fails just that task.
- **A server that says no with its own error object is surfaced on the FIRST occurrence** (2026-09-23). oMLX answers HTTP 200 with `{"error": {"code": "prefill_memory_exceeded", …}}`; SwiftLLMKit ≥ 0.0.209 throws that as `LLMProviderError.responseFailed(code:message:)` instead of a parse failure, and the run loop posts it at once (still retried — it is transient) rather than hiding it behind the ≥5-consecutive gate. Memory refusals are recognized by the typed `LLMProviderError.serverMemoryExhaustion` (the server's `error.code`, never its prose): **three in a row** shrink the agent's context once per streak — the same reduction a context overflow uses — and post a user-addressed `.advisory` (`.warning`) with the server's reason and what to change (free server memory, the server's own memory ceiling, the role's "Max context tokens"). Any other outcome ends the streak. Add a `ServerMemoryExhaustionCode` case when another server spells this differently.
- **A worker's task binding is `taskForAgent(agentID:)`, never "whatever is running."** Anything that resolves "the task" for a running agent — context rebuild, tool routing, usage attribution — must go through the agent's own assignment. `allTasks().first(where: { $0.status == .running })` is not a synonym: `allTasks()` sorts newest-first, so with concurrent workers that lookup returns the most recently created running task to *every* caller. `AgentActor.rebuildContextFromTask` did exactly this until 2026-07-25, and a worker that compacted while a second worker was live came back re-seeded with the other task's title, ID, description, and progress log — then destroyed uncommitted work it no longer remembered doing. Same reasoning as the no-fallback-model rule (roles section of `CLAUDE.md`): it fails closed (channel error + `forceAggressivePrune` on its own history), because a coherent envelope belonging to someone else is far more dangerous than a truncated one belonging to nobody.
- **Address a worker by TASK, never by role.** `agentIDForRole(.brown)` / `supervisor.firstHandle(role: .brown)` returns the OLDEST live worker — Brown is a pool, so that's an arbitrary answer to "which worker?" whenever `maxConcurrentWorkers > 1`. Use `OrchestrationRuntime.liveWorkerID(taskID:)` (exposed to tools as `ToolContext.workerIDForTask`), which resolves task → worker and agrees by construction with `taskStore.taskForAgent` in the other direction. Migrated 2026-07-25: `message_brown` — now `notify_brown` — (which had no `task_id` at all, so every message went to the oldest worker and was labelled with *that* worker's task) and `amend_task` (which guarded on `assigneeIDs` so it never misdelivered, but silently dropped amendments for any task whose worker wasn't the oldest while telling Smith they'd land on the next start). A role lookup on `.brown` is still fine for a *presence* check — "is any worker alive?", which is all the Brown-activity digest asks.
- **A worker takes in only operational notices about itself** (`OrchestrationRuntime.workerAccepts`, 2026-10-05). A public `.system` notice of an `operationalNoticeKinds` kind (agent lifecycle/recovery, rate limit, status digest, preparing, advisory) reaches a worker only when it carries that worker's task id; Smith, the supervisor, still gets all of them. Before this, one worker's stall warning, Smith's provider errors and the digest woke every live worker for an LLM turn each. Addressed messages (`recipientID`) are never filtered by this rule.
- **There is ONE worker briefing composer: `OrchestrationRuntime.composeBrownTaskBriefing`.** Spawn, respawn, and context rebuild all render through it (the rebuild reaches it via `ToolContext.composeTaskBriefing`). Don't write a second, thinner "just the essentials" version — the one that existed silently dropped the acceptance criteria, the step plan, the workspace directories, and the template-input substitution, so a compacted worker lost the contract it was judged against and the directories it was told to write evidence into, and saw raw `{{placeholder}}` text.
- **In the app target, only `@concurrent` means off-main. `async` doesn't, and neither does `nonisolated`.** The `.xcodeproj` sets `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` (everything is implicitly `@MainActor`) **and** `SWIFT_APPROACHABLE_CONCURRENCY = YES`, which enables `NonisolatedNonsendingByDefault` — so a `nonisolated async` function runs on its *caller's* actor, and the callers are views. `@Sendable` does not strip the default either. `AgentSmithPackage` sets neither, so in `AgentSmithKit` a nonisolated `async` function really does hop off. Consequences: an `await MainActor.run` written in app-target code is usually a **no-op**, and deleting it is required rather than optional — it asserts the surrounding work moved off main when it did not (this is what hid an O(m·n) LCS running on the main thread in `DiffView`). `@concurrent` implies `nonisolated` and must precede modifiers (`@concurrent nonisolated func`; the reverse is a parse error). Both settings are deliberate as of 2026-07-29; `scripts/actor_isolation_probe.swift` reproduces the whole table under each flag set, and ROADMAP.md ("Actor-isolation boundary") has the rejected alternatives. Before moving work off main for speed, **measure** — the same entry records a case where the shape looked identical and the work was 3% of the cost.
- **No continuously-repeating SwiftUI animation; spin with `LayerSpinningSymbol`.** Measured 2026-10-05 (Instruments SwiftUI template + Time Profiler on the live app): a repeating `.symbolEffect` (`.rotate` on running task rows, `.variableColor` in `AgentActivitySpinner`) is an "External: Time" SwiftUI update every frame, and each one re-lays out the whole window — `NSHostingView.layout()` in 77% of main-thread samples, ~55% of a core with nothing happening. In an isolated harness (20 spinners over 1,500 rows) the symbol effect cost 40% CPU and the layer spinner 0.0%: a `CABasicAnimation` runs in the render server and never touches the main thread. Live-ticking labels use `SharedTimelineSchedules.everySecond` so every timer ticks on the same boundary and SwiftUI batches them into one update a second.
