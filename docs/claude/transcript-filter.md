# Transcript severity and filter

_Split verbatim from `CLAUDE.md` (2026-10-07); `CLAUDE.md` keeps the binding summary and links here._

### Severity is an axis of its own, and the transcript filter has a floor

**Decided 2026-09-20 (user): "our tool call filtering — and in fact nearly all our filtering — does not have an option that always surfaces errors and warnings."** That gap was live: a failed tool call was posted with the identical `messageKind` as a successful one, so hiding `tool_output` to quiet the transcript also hid every failure. Seven consecutive `create_task` failures reached nobody and the user's request was abandoned in silence.

- **`MessageSeverity`** (`info < warning < error`, `Comparable`) is orthogonal to `ChannelMessageKind`. Kind = *what this message is*; severity = *how bad it is*. A `.toolFailed` KIND was considered and rejected — it needs a case per failure flavour, splits each family across two kinds, and still cannot express "show me anything bad".
- **`ChannelMessage.severity` is the single accessor**, same discipline as `.kind`. It derives `.error` from legacy `isError: true` rows (the persisted corpus is full of them) and treats a JSON null as absent. It does **not** trap on an unknown value — severity drives display, not control flow — but resolves it to `.error`, because failing toward visible is the point. Never read `metadata["severity"]` by hand.
- **`TranscriptFilter.alwaysShowAtOrAbove`** (default `.warning`) admits anything at or above it. **Order in `matches()` is load-bearing**: `hideErrors` → SCOPE (`taskScope`) → floor → NOISE (participants, tool, kind). Scope decides which pane a message belongs to and the floor must never cross it — otherwise a per-task pane shows another task's errors and `.matchNone`, which exists to show NOTHING, shows them anyway. `hideErrors` outranks the floor: it is an explicit opt-out, whereas the floor exists to defeat filters that hide errors *incidentally*.
- **Severity is calibrated on FREQUENCY as well as gravity.** A level that fires on every call stops being a signal and becomes unfilterable noise. `approvedWithoutReview` is `.info` despite running unjudged (it fires on every call when review is off; it stays visible under its own kind) — **user-confirmed 2026-09-21 after the consequence below was surfaced, so don't "fix" it to `.warning`**; `reviewCancelled` is `.warning`, not `.error`, because a user pressing Stop must not paint the transcript red.
- **The floor is what lets the bottom pane's default be quiet.** `TranscriptViewConfig.conversation` ships with the `toolCalls` and `securityReviews` groups HIDDEN (audited 2026-09-20). The task-scope axis does not reach them — a worker's tool rows carry a `taskID`, but **Smith's do not**, so measured over one real session they were 25% `tool_request` + 23% `tool_output` + 25% `security_review` against **12% actual conversation**. Hiding them is safe only because the floor still surfaces failures and WARN/UNSAFE/unavailable verdicts: of 57 security rows, 53 were routine approvals and the 4 WARNs came through. Don't re-enable those groups to "make errors visible" — that is the floor's job. Known consequence, raised with the user and **accepted 2026-09-21**: `approvedWithoutReview` is `.info`, so with per-emitter review switched OFF those rows are hidden in this pane by default (Smith's carry no `taskID`, so the task pane does not show them either). The alternative — promoting it to `.warning` so the floor rescues it — was rejected because it fires on EVERY call and would be unfilterable. Unhide the Security reviews group if you need to watch them.
- Failed tool calls carry the typed outcome: `postToolOutputToChannel` takes `succeeded` and stamps `.error`. The kind stays `.toolOutput`. Producers write `severity` only — `isError`/`isWarning` are retired as writes (`isWarning` had twelve writers and zero readers).

### The transcript filter is one participant × activity relation (redesigned 2026-10-01)

**User request (2026-10-01): "it's so complicated how it works makes little sense … redesign it."** The previous model exposed ten overlapping axes — a sender allow-list, a separate recipient allow-list, a public/private switch, default message kinds, per-sender kind overrides behind a modal "For: \<sender\>" picker, per-tool hiding, a "show errors" switch, a separate severity floor, and a task-scope switch that was a dead control in the task pane. `TranscriptViewConfig` is now:

- **`hiddenParticipants`** — hiding someone hides messages FROM them and private messages TO them (`TranscriptFilter.hiddenParticipants`, keyed on `MessageRecipient.participant`). This replaced sender + recipient + public/private, which had to be kept in step by hand to say "hide Brown".
- **`selections: [Sender: TranscriptKindSelection]`** — the participant × activity relation, sparse (a participant without an entry shows everything; `setSelection` drops an entry that returns to `.allVisible`, so equivalent configs are `==`, which preset matching relies on). Every UI row — a category, a single kind, a tool family, a single tool — is a set of `TranscriptFilterTarget`s, so ONE aggregate (`visibility(of:for:)`) and ONE mutation (`setVisible(_:targets:for:)`) serve every checkbox. The popover shows it as an "Everyone" list or a "By participant" grid of the SAME data — never a hidden per-sender mode.
- **`problems: TranscriptProblemPolicy`** — one choice replacing `showErrors` + `alwaysShowAtOrAbove`, whose combinations had no sensible reading. It maps onto the filter's unchanged `hideErrors` + floor.
- **`hideTaskScoped`** — offered only in the session pane (`TranscriptPane.offersTaskScopeControl`); the task pane forces its own scope and its preset matching ignores the switch.
- **`TranscriptPane`** owns each pane's default and presets (session: Conversation, Everything; task: Everything, Condensed). The header button names the active preset or "Custom"; its funnel fills only when the pane differs from ITS OWN default.
- **Identity is the AUTHOR, not the poster** (fixed 2026-10-02). `ChannelMessage.author` / `addressee` are the single accessors every identity reader uses — the filter's participant and per-participant axes, its counts, and the transcript row header. A Security Agent verdict is posted `.system` but authored by `.agent(.securityAgent)` (derived from the typed `kind`) and addressed to the agent it reviewed (`attributedRole`, the `agentRole` stamp). Before this the filter called every verdict "System" while its text read "Security Agent → Brown".
- **A role becomes a participant only through `ChannelMessage.Sender.participant(for:)`** (fixed 2026-10-02). `AgentRole.validator` is spelled `.validator` in the transcript, never `.agent(.validator)`; `author`, `addressee`, `MessageRecipient.participant` and `TranscriptViewConfig.participants` all go through that one exhaustive mapping. Every Security Agent verdict carries its reviewed role (`postSecurityReviewToChannel(reviewedRole:)`, required) — the validator's evidence-call verdicts used to carry none, so "hide Validator" missed them — and the validator's also carry the task id, so they land in the task's pane with their request. `TranscriptDelivery` joins a hidden verdict to its call by (`agentID`, call id): a provider call id alone repeats across agents.
- **"Who writes this kind" has one table: `ChannelMessageKind.fixedAuthor`** (2026-10-02). `author` reads it first, and `TranscriptFilterTarget.applies(to:)` derives from it, so a verdict class or tool-scope switch applies only to the Security Agent. `setSelection` is the one write path and strips switches a participant cannot use (the memberwise init and decode go through it), `visibility(of:for:)` skips inapplicable pairs, and the grid blanks those cells — otherwise a preset and a config that shows the same thing compared unequal ("Custom") and the grid offered checkboxes that did nothing. `matches` is unchanged by this: it always keyed verdict state on the author.
- **Counts follow the filter's own participant rule.** `TranscriptFilter.excludesByParticipant` is the single definition `matches` applies; `TranscriptFilterStats.counts` leave out what it hides. `involving` (the chips) and `problemCounts` are deliberately NOT narrowed. An open popover recounts at most once a second as `messagesRevision` moves (`Observations`, macOS 26), restarted on a config or pane change.
- **Shown-only-as-a-problem is surfaced, not silent.** `TranscriptFilterStats.shownOnlyAsProblems` / `problemCount` count messages the problem policy re-admits; the summary line, the Problems caption, and an orange note on each hidden activity row say how many. Without this, unchecking a row whose WARN verdicts stayed visible looked like a broken filter.
- **Security verdicts filter by CLASS, and hiding one never strips a tool row of its status** (2026-10-02, user request). `SecurityVerdictClass` (accept / warn / block) is classified from the typed `securityDisposition` tag via `ChannelMessage.securityVerdictClass` — never from verdict prose; a missing tag fails toward `.block` (visible). The Security reviews category's children are Accepted / Warnings / Denied or blocked (`TranscriptFilterTarget.securityVerdict`) plus Tool scope (`.toolScopeReview`, posted by `SecurityEvaluator.postToolScopeResult` after each successful scoping pass). `.securityReview` is filtered ONLY through `TranscriptKindSelection.hiddenVerdictClasses`; a legacy hidden `security_review` kind normalizes to all classes hidden. **The tool row's verdict icon + popover is always shown**; the filter decides only whether the full verdict text also renders inline below it. Mechanism: panes fetch through `TranscriptDelivery` (= `matches` ∪ the verdict of each tool call the pane was delivered), and `ChannelLogView.verdictFilter` (in `CacheSignature`) decides which verdict rows render as text. Don't fetch through `matches` alone — the tool row then loses its checkmark. Don't deliver a hidden verdict whose call ISN'T delivered either: it never draws, and the Conversation preset (tool calls hidden) would fill its bounded render window with them. A verdict carries no tool name, so `TranscriptDelivery` is stateful (requests awaiting a verdict, carried across batches per `TranscriptStore` subscriber, rebuilt on every reset).
- **MCP tools group by server** in the activity tree via `MCPToolNaming.components(of:)`, the exact inverse of `prefixedName` (kept beside it), so rows show the tool's own name instead of a truncated `mcp__<server>__` prefix.
- **Live counts** come from `TranscriptFilterStats`, computed off-main with the same `TranscriptFilter` the pane renders through — never a second implementation of "would this show".
- **Migration** of every earlier on-disk generation is exact per participant (old override if any, else old default); sender exclusions become hidden participants; a recipient-only exclusion and public/private are dropped (both fail open; no saved config used them). `TranscriptViewConfigTests` pins both of this machine's real persisted configs migrating correctly. A downgrade reads the new format as show-everything (fails open).
