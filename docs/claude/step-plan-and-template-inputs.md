# Step plan and template inputs

_Split verbatim from `CLAUDE.md` (2026-10-07); `CLAUDE.md` keeps the binding summary and links here._

### The step plan (`manage_steps` / `TaskStepAction`)

A task's `steps` array is the worker's ordered plan and part of what validators judge. Rules that hold everywhere:

- **`delete` is the single producer of `.removed`.** `set_status` covers only the four REVERSIBLE states (pending / in_progress / completed / skipped) and rejects `.removed` outright; the tool schema doesn't offer it either. Tombstoning is terminal and irreversible, so it gets its own verb rather than hiding as a one-way trapdoor in a status setter. `TaskStep.Status.removed` remains the persisted representation — this is about the mutation vocabulary, not the model.
- **A tombstone is never resurrected.** Any path that freshens a plan (template instantiation, failed-task retry) resets the ACTIVE steps and leaves `.removed` steps removed. Template instances drop the template's tombstones entirely — those are the template's authoring history, not the run's.
- **Whoever replaces the array wholesale (`TaskStore.setSteps`) must pass the tombstones back through.** `setSteps` writes exactly what it's given, so an active-only array silently erases the append-only record. Editors carry them in a preserved bucket and re-append.
- **Retry resets the plan; reopen does not.** `resetFailedTask` returns active steps to `.pending` and clears skip notes (a retry re-runs everything). `reopenCompletedTask` deliberately leaves statuses alone — reopening means "the work landed but something's incomplete", so completed steps really were completed.
- **`move` is the preferred repositioning verb.** `reorder` demands every active step id restated, so one concurrent add invalidates the call; `move` repositions a single step via `before_step_id` / `after_step_id` / a 1-based `position` and requires exactly one of the three. Both keep tombstones parked after the active steps.
- **`purge` hard-deletes, and is Smith-only.** It removes the row entirely — no tombstone, no note, no record — so it is gated twice: the tool refuses any role but `.smith` and omits the action from Brown's schema *and* description, and `TaskStore` refuses unless `AgentTask.isStepPlanPurgeable` (templates always; every other task only while `startedAt == nil && validation == nil`). `validation == nil` alone is insufficient — a task with no acceptance criteria can run to completion without ever opening a ledger. Purge is for shaping a draft or template plan; `delete` is the honest verb everywhere else.

### Template inputs (`{{placeholder}}` substitution)

A template task defines `templateInputDefinitions`; `instantiateTemplate` resolves the run's values and renders them into the instance. **Built 2026-07-28** — before that, substitution reached the instance TITLE and nothing else, so a description reading `Build {{app_name}}` shipped to the worker with the placeholder intact and the values appended below as a separate `## Template inputs` block.

- **Substitution covers every authored field.** Title, description, each ACTIVE step's text, and each criterion's `name` / `validationPrompt` / `inputEnumeratorPrompt`. `TaskStore.instantiateTemplate` is the definition of that set; the authoring checks mirror it field for field, sharing labels via `TemplateInputValidation.renderableTextFields(ofStep:atPosition:)` / `(ofCriterion:)` so the same offending step reads identically wherever it is caught. The three paths that author a whole template at once — `create_task`, the editor's Create, and the editor's live warning — go through `TemplateInputValidation.firstProblem(authoringTemplateWithTitle:…)`, which takes field GROUPS and never an `AgentTask`: handing it a stored task is how the removed sweep comes back. Criteria are in scope because a validator is handed one criterion verbatim — `the binary must be named {{app_name}}` is as broken by a surviving placeholder as the description is. Tombstoned steps are out of scope because instantiation drops them.
- **Rendering is LENIENT; authoring is STRICT. Both halves are load-bearing.** `TemplateStringRenderer.renderSubstitutingDefinedPlaceholders` substitutes only names that match a definition and passes everything else through byte-for-byte — an undefined name, an unclosed brace, `{{ spaced }}`, `{{NotSnakeCase}}`. Failing the render instead would make a template whose prose legitimately quotes brace syntax (a Handlebars partial, a JSON schema) impossible to RUN, and would break any template authored before this existed. The typo that leniency would otherwise hide is caught by `TemplateInputValidation.placeholderProblem`, which refuses the text when it is WRITTEN. Don't "tighten" the renderer without moving the error somewhere the author can still see it.
- **A `{{…}}` is only a placeholder relative to a definition set.** An empty `definedNames` short-circuits every check to nil. That is what lets an ordinary task's description discuss `{{user_name}}` freely and what keeps such a task promotable to a template.
- **Two renderers, differing on two axes deliberately.** `render` (strict, whitespace-collapsing) is for `templateInstanceTitleTemplate` — a deliberate PATTERN string where an unknown name has no innocent reading. `renderSubstitutingDefinedPlaceholders` takes a `Layout`: `.preserved` for body prose (collapsing would fuse a markdown description onto one line) and `.singleLine` for the plain title, which stands in for the title template when none is set. **`.singleLine` collapses only when a placeholder was actually substituted** — the collapse repairs the gap an omitted optional input leaves, so text substitution never touched must return byte-for-byte. Collapsing unconditionally silently rewrote the title of every instance (`Nightly  report` → `Nightly report`) even on templates defining no inputs.
- **Every write validates the text IT writes, against the definitions that will then be in effect — and nothing validates more than that.** `updateDefinition` checks only its title and description; `updateDescription`, `setSteps`, `applyStepAction` `.add`/`.update`, `setAcceptanceCriteria`, and `applyCriterionActions` `.add`/`.update` check only their own text; `setTemplateInputDefinitions` writes no text and so checks none. `TaskStore.addTask` cannot refuse, so `CreateTaskTool` and `AppViewModel.createManualTask` check every field BEFORE creating — nothing half-lands.
- **There is deliberately no whole-task sweep, and re-adding one BREAKS RENAMING AN INPUT.** Both variants were written and removed the same day. A new name cannot appear in a step until it is defined, and the definition cannot change while a step still names the old one — neither ordering is legal and no third call does both, so the guard could be entered with no exit. It also broke the task editor outright, which saves the definition first and the steps second: a user who correctly renamed the input AND fixed every step in one sheet had the save refused over step text the next call was about to replace. The accepted cost is that removing an input can strand a `{{name}}` in text the call doesn't touch; it renders as literal text, the editor flags it live across the whole prospective task, and the next edit of that text refuses it. Every repair path (`delete`, `purge`, `move`, `reorder`, `setStatus`) is unvalidated, so an orphan is never locked in.
- **The instance title falls back to the RENDERED template title, composed once and shared by both branches.** When an instance-title template renders to nothing, the fallback is the template's own title *after* substitution — not the raw text. Composed twice, the copies disagreed: a template titled `Localize {{app_name}}` fronted by an optional `{{locale}}` title template showed a placeholder for an input the run had actually supplied. Empty after rendering (every placeholder optional and blank) keeps the author's raw text; failing instead would let a cosmetic title veto a recurring scheduled run forever.
- **Error messages quote a BOUNDED span, and the unclosed-brace case quotes a window, not a prefix.** `TemplateStringRenderer.validate` now runs on authored body prose — markdown that reaches thousands of characters — so interpolating the whole template buried the one sentence that said what was wrong. `unclosedPlaceholderProblem` reports a character offset plus a window around the offending braces, because that case has no placeholder NAME to fall back on and the scan reaches the bad `{{` only after passing every well-formed one before it: a leading prefix would show text that is not the problem. `quotedForMessage` prefix-truncates only spans whose first character IS the problem.
- **`amendDescription` checks the amendment on a template**, the third writer of `description` and formerly the only one that didn't. A typo there welds into every future clone. Only the amendment is checked, never the description it lands on, and the check sits ABOVE the dedup so a re-sent bad amendment can't fall into the no-op branch and report success.
- **An amendment to an INSTANCE substitutes the run's supplied input values at amend time** (2026-07-28) — before this, instance amendments (including `run_task`'s deferred template amendment, which lands on the instance) were the one authored-text path substitution never touched, so "also sign `{{app_name}}`" reached the worker literally. `definedNames` is the instance's VALUE key set, because instances carry values but not definitions — a name with no supplied value (omitted optional, or a typo) stays literal, deliberately: for an after-the-fact amendment the visible placeholder is the honest outcome, not a silent empty gap. The dedup compares the SUBSTITUTED text, which is what any earlier send appended.
- **The `## Template inputs` name→value block renders ABOVE the description** (2026-07-28, user decision) — composed at render time by `renderedDescriptionWithTemplateInputs()`, never baked into the stored `description` (the stored values stay the single source; old instances pick the placement up retroactively). That one composition feeds the worker briefing, the validator's `taskDescription` slot, the transcript banners, prior-task retrieval queries, and the task-detail UI's Description display/copy. The description EDITOR still seeds from the raw `description` — the block is derived, not authored, and must never round-trip through an edit.
- **The task editor's live warning is built from the SAME lists `save()` writes** (`builtInputs` / `builtCriteria` / `builtActiveSteps`). Numbering over raw rows made it say "step 3" where the store said "step 2", quoting a raw row named a criterion the store called something else, and an enumerator-only row produced a warning about text `save()` discards. That warning is advisory and never disables Save — deliberately, since it is the only surface that shows a placeholder stranded by a removed input.
- `updateDescription`, `setSteps`, and `amendDescription` return `String?` (a refusal) rather than `Bool`/`Void`; their callers used to invent a reason that could only ever name one of the ways they fail. `amendDescription` is deliberately not `@discardableResult` — a silently dropped refusal is the defect it closes.
